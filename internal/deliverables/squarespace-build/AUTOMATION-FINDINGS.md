# Squarespace migration — what can and can't be automated

*Researched July 2026, verified against live Squarespace docs (not memory). This is the
final answer on "can a tool move the prototype into Squarespace for us." Don't
re-research it; if Squarespace ships a content API later, update this file.*

## The verdict

**The visual build is manual. No API, MCP, importer, or third-party service will
assemble our pages in Squarespace 7.1.** This is now confirmed, not assumed. But three
levers cut the manual labor a lot, and the build kit is set up to use all three.

## What we checked (and what's true)

| Hoped-for shortcut | Reality | Source |
|---|---|---|
| A Squarespace **API** that creates/edits pages, sections, or blocks | **Does not exist.** The entire API surface is 14 APIs: Commerce (Products, Orders, Inventory, Transactions), Contacts, Profiles, Forms, Domains (search + management), Reseller, Incoming Webhooks, Webhook Subscriptions, Scripts, UI Component Registrations, Acuity. None write page content. | [Developer Tools APIs list](https://support.squarespace.com/hc/en-us/articles/41325887099533-Developer-Tools-APIs-at-Squarespace), [developers.squarespace.com](https://developers.squarespace.com/) |
| A **Squarespace MCP** that builds pages | The community "Squarespace MCP" servers just wrap those same commerce APIs. No page-builder MCP exists. | web search, July 2026 |
| **Developer Mode** (Git / local custom templates) | **7.0 only.** Not available on our Build-Your-Own 7.1 site. No template-code backdoor. | Squarespace Developer Platform FAQ |
| Import our **hand-built HTML** prototype | **No importer accepts arbitrary HTML.** Squarespace only imports from WordPress, Blogger, Tumblr, Wix, Shopify, Big Cartel, and Squarespace-to-Squarespace. | [Importing and exporting content](https://support.squarespace.com/hc/en-us/articles/205814028-Importing-and-exporting-content) |
| A read-only "content is an API" (`?format=json`) that we could round-trip | Read-only. Good for pulling data out, useless for building pages in. | developers.squarespace.com |

Note: one web-search summary claimed a "Pages Endpoint" that creates pages. That was a
hallucination; the official API list has no such endpoint. Flagging it so we don't chase
it again.

## The three levers we DO use

### 1. Text + markup is paste, not retype
Copy-paste from the *rendered* prototype (in a browser) into a native **Text block**
preserves headings, bold, italic, links, and lists. For long-form pages, a **Markdown
block** (exists in 7.1, and supports h4–h6, which the WYSIWYG editor does not) is an even
faster paste. **No approved copy is ever retyped** — which also protects the wording
stakeholders have already signed off on. The per-page build packets carry this copy in
paste-ready form.

### 2. The arboretum (36 trees) bulk-imports via WordPress WXR
This is the one many-items, preserved-URL case, and it's the single biggest automation
win. The WordPress importer accepts an uploaded **WXR/XML** file (the "advanced" option)
and creates blog posts under a collection.

- **All 36 tree slugs in the prototype have an exact-matching WordPress `post`** in
  `assets/wordpress-export/` (100% coverage), each already carrying its full memorial
  dedication + species writeup. The WXR is a clean 1:1 extract, not a messy split.
- A blog collection slugged **`arboretum`** yields `/arboretum/[tree]` — exactly the
  QR-code URLs. The importer "attempts to preserve" the post slug; a post's slug is
  editable per-post if it doesn't.
- Generated by `make-arboretum-wxr.py` → `arboretum.wxr` (36 trees) and
  `arboretum-TEST-1-tree.wxr` (marshall-smith only, for the safety test).
- **Safety protocol (non-negotiable, QR codes depend on it):** import the 1-tree test
  first, confirm the published URL is exactly `/arboretum/marshall-smith`, THEN import
  the full 36. Do not bulk-import before the test URL checks out.
- **Content caveat:** the WXR content is the *old WordPress* copy. It's more complete than
  the prototype (the prototype shows "Species to come" placeholders), but it should get a
  quick accuracy pass before go-live — some entries link to old PDFs on
  `allsaintsconcord.org` that will need updating.

### 3. Pre-built everything that isn't drag-and-drop
The build kit already ships the parts that would otherwise be tedious to derive:
- **Global CSS** (`library/custom-css-global.css`), **head/footer injection**
  (`library/*-injection.html`) — paste once, inherited everywhere.
- **The two raw Code Blocks** (`library/sections/hero.html`, `community-bento.html`) — the
  only two sections native blocks can't do.
- **Per-page build packets** — final copy in paste-ready form + a section-by-section
  native-block map + image list + alt text + link targets, so each page is
  follow-the-checklist-and-paste instead of reverse-engineering the prototype.

## Bottom line for time budgeting
- **Global setup:** one-time, ~1 sitting (`00-global-setup.md`).
- **Homepage:** the hard one; build first, log real behavior in `DISCOVERIES.md`.
- **Arboretum:** minutes, via WXR (after the 1-tree test).
- **Every other page:** assemble from the repeating patterns using its build packet;
  copy pastes in, layout is dragged in. No content retyped.
